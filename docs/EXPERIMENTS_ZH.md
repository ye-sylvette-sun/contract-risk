## 1. 我们在问什么

数据集告诉我们，哪些条款**事实上**被法院拿去解释过。实验反过来问：

> 给模型一份合同和它的全部条款，但**不告诉它答案**，它能不能自己指出哪几条会成为法庭上被攻击的目标？

难点在于比例。一份合同里被法院争过的条款通常只有个位数，其余几十上百条都没人碰过——整个评估集里 positive 只占 **1.6%**。所以这是一道"大海捞针"的题，模型很容易靠"多标一些"来刷成绩，评分时必须防住这一点（见第 5 节）。

---

## 2. 每次调用，模型拿到什么

**一份合同 = 一次调用**，一次把这份合同的所有条款判完。不切成小批，因为第 2 类风险问的是"这一条和别的条款有没有冲突"，把合同切开就等于把问题变简单了。

每次调用的输入包含四块：

**① 判断标准。**两大类风险的定义（和数据集用的是同一套：第 1 类看条款本身的文字，第 2 类看它和合同其余部分的关系），外加几条校准要求：不要因为条款重要就给高分；给第 1 类打高分必须能**点出**是哪个词有歧义；给第 2 类打高分必须能**点名**是和哪一条冲突。

**② 三个示范例子**，每种 risk type 一个。每个例子是同一份合同里的**一对**条款：

- 一个法院**真的解释过**的条款，**外加判决书里讨论它的那段原文**——让模型看到当时双方到底在争什么、法官觉得哪里不清楚；
- 同一份合同里**没被解释过**的一条，标为"风险较低"。

每个例子还会说明那份合同的实际比例（如"这份合同 3 条被解释过、95 条没有"），让模型知道该期待什么样的基数——但明确说这是**参考基数，不是要凑的指标**。

**③ 待判合同的全文。**

**④ 要判断的条款清单**，每条都是从合同里逐字摘出来的原文。这里有个关键处理：条款的编号一律换成 **`c001`、`c002`…** 这样的匿名编号，**按它们在合同里出现的先后排序**。

> 数据集现在的编号本身就是按文档顺序排的 `c001…`，由 step 1 在任何东西知道标签之前分配，不含答案。实验仍然重新编号一次，让它不依赖数据集怎么给行做 key。这一步原本是必需的：早先的编号是 `pos1`、`neg7`，`pos` 开头的就是答案，等于把答案写在每扇门上。

## 3. 模型要交回什么

对**每一条**条款，交回一个 **issue list**（问题清单），而不是两个数字。清单里每一项对应一个**具体的**、法院可能拿去解释的毛病：

| 字段 | 内容 |
|---|---|
| `issue` | 两句话，点名**这一个**毛病：第 1 类要点出到底哪个词有歧义，第 2 类要**点名它和哪一条对不上**。没有具体毛病可点时填 `null` |
| `type` | `1` = 条款自身文字的毛病；`2` = 它和合同其余部分关系上的毛病 |
| `prob` | 0–1，两位小数，**就这一个 issue** 会让法院有东西可解释的概率 |

**为什么不是两个数字。** 一个条款完全可能同时有"某个词含糊"+"清单范围不清"+"和三节之外的定义打架"三个毛病，强弱还各不相同。两个数字说不出这件事，清单可以，而且每个毛病的强弱是分开说的。

**清单通常很短，这一点是明确要求的：**

- **绝大多数条款一个具名 issue 都没有。** 它们的答案是恰好两项、每类一项，`issue` 都填 `null`，`prob` 照样给出"这类争议大概有多可能"——两个都远低于 0.5。这是最常见的答案。
- 其次常见的是**一个具名 issue + 另一类的一个 `null` 项**。
- **同类多个 issue、或者两类都有具名 issue，属于例外情况。** 只有当那个额外的毛病**很明显**、单独拿出来也配得上一个高概率时才写。拿不准的第二个 issue 就不是第二个 issue——不要写，让第一个 issue 的概率去承载这份不确定。判断标准：这第二个毛病，单独讲给法官听，他会当回事吗？
- **任何一类都不能缺席。** 某一类完全没有条目会被读成概率 0，那是比"我没发现具体问题"强得多的断言，所以才要那个 `null` 项来承载概率。

概率要求写到小数点后两位（0.03、0.17、0.62），不许四舍五入到 0.05 或 0.1，因为我们真正在意的是条款**之间**的高低排序，而不是某一条的绝对分值。

**打分时怎么从清单得到两个数。** `prob_type1` / `prob_type2` 取的是**该类型下最强的那一个 issue**，不是求和——概率是逐 issue 且互相独立的，两个弱 issue 不该叠成一个强的；每个面板问的本来就是"会不会因为**其中任何一个**而被法院解释"。这段逻辑只有一份实现（`predictions.probs_of()`），两个实验臂和 Spellbook 打分器共用。

如果模型漏判了一部分条款，程序会**追问一次**（**续用同一个会话**，列出漏掉的编号让它补齐——这些编号它可以对着自己已经写下的东西核），而不是把漏掉的直接当成"低风险"——否则测的就是我们的流程，不是模型。

## 4. 怎么跑

| | agent 模式 |
|---|---|
| 形式 | 一个 Claude Code 会话判完一份合同，跑在容器里 |
| 合同 | 工作目录里的一个文件 |
| 怎么读 | 自己决定：读、回头再读、搜关键词 |
| 怎么交答案 | 自己写成文件，可以分批写 |
| 模型 | `claude-opus-5`，effort `high`，上限 100 turns |
| 计费 | Claude Code 订阅（容器里不存在任何 API key） |

之所以用 agent 而不是一次性调用：第 2 类风险本质上是在一份几十万字的文件里做检索，
一次性调用只能凭一遍阅读作答，而 agent 可以回头翻。

评估用 **100 份合同、11,636 个条款**（其中 190 个 positive，占 1.6%）。另外 3 份合同
永久留作示范例子，不参与评估，保证模型没在自己被考的题上学过。

---

## 5. 怎么评分

概率 ≥ 某个阈值就算模型"标出了"这一条。我们看三个数：

- **精确率**：模型标出来的条款里，有多少真的被法院争过；
- **召回率**：真的被争过的条款里，模型找出来了多少；
- **标记比例**：模型一共标了多少条。

第三个数是防作弊用的。在 1.6% 的基数下，一个把整份合同标出三分之一的模型也能有好看的召回率，所以召回率必须和标记比例一起看。

另外还看两个不依赖阈值的**排序**指标（AUC）：不管阈值定在哪，模型有没有把真正被争过的条款排在前面。在 1.6% 这么低的基数下，**PR-AUC 是最该看的那个数**。

## 6. 结果

一次运行，`agent`，跑完全部 100 份合同、11,636 个条款——100 个会话、1,254 turns，
没有漏判，没有任何一个会话触到 turn 上限。完整分析见 [REPORT.md](REPORT.md)。

| 面板 | 正样本 | ROC-AUC | PR-AUC | 精确率@0.5 | 召回率@0.5 | 标记比例 |
|---|---:|---:|---:|---:|---:|---:|
| 有风险 vs 无 | 190 | **0.899** | 0.361 | 0.35 | 0.53 | 2.5% |
| 第 1 类（自身缺陷） | 141 | 0.898 | 0.326 | 0.31 | 0.50 | 2.0% |
| 第 2 类（条款冲突） | 81 | 0.854 | 0.149 | 0.21 | 0.22 | 0.7% |

主面板 ROC-AUC 的 bootstrap 95% 置信区间是 **[0.844, 0.949]**。在 1.6% 的基数下
**该看 PR-AUC**：ROC-AUC 被 11,446 个容易的负样本抬高了。两类风险的排序能力基本
持平，置信区间大幅重叠，所以 0.045 的差距**不构成已确立的差异**。

阈值 0.5 处的标记比例（2.5%）接近真实基数（1.6%），说明召回不是靠多标换来的。

**要达到某个召回率要读多少**（有风险 vs 无面板）：

| 召回率 | 阈值 | 精确率 | 标记比例 |
|---:|---:|---:|---:|
| 70% | 0.41 | 0.182 | **6.3%** |
| 80% | 0.33 | 0.079 | 16.6% |
| 90% | 0.26 | 0.044 | 33.5% |

抓住 70% 被争过的条款只要读 **6.3%** 的合同。再往上曲线急转：80% 要读 16.6%，
90% 要读三分之一——到那一步排序已经不起作用了。

**合同长度不影响表现**：短（9–58 条）/ 中（60–148）/ 长（153–698）三档的 ROC-AUC
分别是 0.864 / 0.897 / 0.876，差距远在置信区间之内。698 条款的合同和 20 条款的信函
排得一样好。

**成本**：1,890 input + 8.6M cache-create + 55.8M cache-read + 2.4M output token，
容器运行 7.6 小时，**按 API 价折算 $174.35**——实际走订阅额度，不是真实账单。每个
条款约 209 个 output token，缓存吸收了 85% 的输入侧。

**几个必须记住的限度**：

- **跑与跑之间的波动没有测量**（没设温度、没设随机种子），重跑不会得到同样的数字。
  旧设计下同条件重跑一次，ROC-AUC 动了约 0.02、召回率@0.5 动了约 0.10——上面所有
  小差距都该按这个尺度来看。
- **长度是一条真实的捷径**：单靠条款长度排序，合同内 ROC-AUC 已经有 **0.706**，
  任何模型的 AUC 都必须拿它当基线来读。上面表格所在的旧数据集是 0.523，但那个
  数字才是假象——当时的正例是由读过判决书的模型切的，边界贴着争议语言而不是包含
  它的完整条款。见 DATASET_ZH.md。
- **negative 的含义是"没人争过"，不是"写得没问题"**，所以精确率是个下界。
