# 预测实验（中文）

**问题。** 给定一份合同和它包含的条款，模型能否说出哪些条款会被联邦法院拿去解释？

> **实验是 agentic 的。** `risk_detect_agent.py` 每份合同跑一个隔离的 Claude Code
> session，§8 报告的就是它。taxonomy、worked example、gold 映射和 `preds.csv` 的行
> 格式都放在 `runs.py`，因此运行和给它打分的一切不会对某一列的含义产生分歧。没有
> 任何地方直接调用 Anthropic API，所以不需要 `ANTHROPIC_API_KEY`。

**实验留在 Claude 上**，而数据集构建用 OpenAI。agent 这一路**就是** Claude Code
CLI，所以这不是一个自由选择。`lib.provider_of()` 从模型名判断传输方式。

---

## 1. 评测集

三份 example 合同持出，连同同案的其他文书 —— 同案文书会作为 `context/` 挂载，判断
一份 example 的同案兄弟等于把该 example 的构造条款和法院原话直接摆在模型面前。

```
全语料   87 份合同 / 10,102 个条款
持出     3 份 example 合同
评测集   84 份合同 / 9,890 个条款
gold     163 个被解释条款（type1 120，type2 68）
```

---

## 2. 每次调用，模型拿到什么

一个工作区，挂载为容器里的 `/work`：

```
contract.txt      被判断的合同全文
provisions.json   要判断的条款，逐字引用，带 id
context/          同案提交的其他文书（如果有）
examples/         三份 worked 合同，每份一个目录
```

`examples/` 里每份合同一个目录，展示该合同**被法院解释过的每一个条款**、其中**每一个
不同的缺陷**、以及显示争议的判决书原文段落。三份之间：一份只有 risk type 1，一份只有
risk type 2，一份两者都有。重复出现的段落和摘录以交叉引用代替重复打印。

每份 example 还带一个**该案中没有被解释**的条款作为对照 —— 它是弱得多的证据，且
**不**代表该条款没有问题：它可能起草良好，也可能带着无人有机会去争的潜在缺陷。

---

## 3. 模型要交回什么

每个条款一条判断：

```json
{"clause_id": "c042", "issues": [
   {"issue": "……", "type": 1, "prob": 0.34}
]}
```

- `issue` —— 两句话，指出**这一个具体缺陷**。type 1 引用那个词或短语并给出两种读法；
  type 2 点名文书的另一部分，并说清这一对留下了什么悬而未决。
- `type` —— `1` 表示问题在本条款自己的文字里，`2` 表示在本条款与文书另一部分的关系上。
- `prob` ∈ (0, 1] —— 法院会**因这个 issue** 而有东西需要解释的概率，保留两位小数。

**空列表是合法答案**，表示这个条款上说不出任何缺陷。一个类型没有条目，等价于该类型
概率为 0。

### 类型判定

核心测试：**假设那条对手条款不存在，这一条还有疑问吗？** 还有 → type 1，这一条自己
就说不清，对手条款只是某一方用来支持某种读法的论据；没有了 → type 2，两条各自都清楚，
是并排放在一起才出问题。

另一个角度是法官要不要动用解释准则：关系型缺陷会让法院去调和两条、给每一条都留出效力、
避免让其中一条变成赘文；条款自身的缺陷不需要任何准则，法院只是引用那个词、然后列出
双方各自的读法。

`ambiguous`、`plain meaning`、`reasonable interpretation`、`read together` 这些词两类
都在用，不能作为判据。

## 5. 隔离

agent 跑的是 Claude Code CLI，它可以加载 settings 文件、`CLAUDE.md`、memory、skill 和
MCP server，而这些都不会出现在对话里。容器里没有 `~/.claude`、没有 settings、没有
skill、没有托管策略，只有该合同的工作区被挂载 —— `dataset.csv` 和其他合同根本不在它的
文件系统上。

`preflight.py` 逐项核对这些，并核对计费模型确实是所请求的那个。详见
[REPRODUCIBILITY_ZH.md](REPRODUCIBILITY_ZH.md)。

## 6. 怎么评分

三个 one-vs-rest 面板。**两个 risk type 面板是 one-vs-rest**：对 risk type 1 而言，
一个 type-2 的 gold 条款算作 negative —— 因为两个概率是各自独立的判断，不是同一个分布
的两个份额。

模型从未返回判断的条款（`ok=0`）保留在评分中，两个概率都置 0：沉默是一次「无风险」的
预测，不是删除该行的理由。

## 8. 结果

84 份合同、9,890 个条款、84 个 session，无一条款未判断，按 API 等价费率
**$169.47**。

| 面板 | positive | ROC-AUC | recall 天花板 | P@0.5 | R@0.5 | 标记率 |
|---|---:|---:|---:|---:|---:|---:|
| risky vs not | 163 | **0.868** | 0.99 | 0.30 | 0.16 | 0.9% |
| risk type 1 — 条款自身 | 120 | **0.770** | 0.72 | 0.34 | 0.14 | 0.5% |
| risk type 2 — 关系型 | 68 | **0.690** | 0.59 | 0.13 | 0.07 | 0.4% |
| 仅按条款长度 | | **0.691** | | | | |

**每一个数字都要对照长度基线读。** 在 risk type 2 上模型没有超过它：0.690 对 0.691。
这次运行相对「按条款长度排序」的全部增益，都在 risk type 1 和那个二元问题上。

recall 天花板是阈值取 0.01 时可得的 recall —— gold 条款中拿到过该类型任意概率条目的
比例。它必须和产生它的标记率一起读：模型在 68% 的条款上都写了至少一条 issue，所以
`risky` 上 0.99 的天花板意味着几乎每个条款都拿到了点什么，而不是几乎每个被解释的条款
都被识别出来。

图：`output/figures/risk_detect_agent_threshold_curves.png` 与
`issue_alignment_threshold_curves.png`。[REPORT_ZH.md](REPORT_ZH.md) 解读它们。

**运行间方差未量化**：没有随机种子，没有温度控制，同一 prompt 从未在这个数据集上跑过
两遍。在做过这件事之前，任何两个配置之间的差异都不应被称为真实差异。
`compare_risk_detect.py --against` 就是用来测这个的，尚未用于此。

## 9. issue alignment 检查

风险检测在模型把被诉讼条款排到高位时就记一次命中。它看不出**模型说出的那个缺陷**是不是
法院解释的那一个。一个把正确条款因错误理由标出来的模型，得分和真正理解了争议的模型完全
一样，而据此行动的审阅者会看错地方。

`issue_alignment_check.py` 补上这个缺口。对 agent 说出的每一条 issue，由**另一个**模型
读取该条款、这条 issue、以及 step 2 为该条款记录的**全部**缺陷（各带自己的逐字段落），
说出这条 issue 对应其中哪一个、以及有多接近。

| | |
|---|---|
| precision | agent 说出的 issue 中，有多少说的是法院真正解释过的缺陷 |
| recall | 语料中 225 个缺陷里，agent 找到了多少 |

**判官是 `gpt-5.6-sol`，effort high** —— 刻意不使用被评模型所属的家族。

**判官看得到什么、看不到什么。** 条款、issue 正文、候选缺陷及其段落。**看不到** agent
给的概率（会形成锚定）、看不到该条款是否为 gold（这在调用前就已确定）、也**看不到任何
一方的 risk type**。

**risk type 完全不参与。** 候选不按类型过滤，类型也不展示。数据集的类型标签来自案件的
Westlaw key 而不是判决书段落 —— 62 个案件中有 41 个的 key 只覆盖一个主类型，该案每个
缺陷都取那个类型 —— 按它过滤会丢掉那些「双方说的是同一个缺陷、只是归类不同」的匹配。
类型一致性单独报告，由 `type` 对 `gold_type` 在匹配对上计算。

**比较是句子对句子。** 两边都是一句话、说一个条款上的一个缺陷。段落是上下文：它显示
法院在解释什么、并确认记录下来的那句话忠实于它，但超过一半的已记录缺陷与同案的另一个
缺陷共用段落，所以仅凭段落无法把两者区分开。

**范围。** 落在被法院解释过的条款上的每一条 issue。落在从未被解释的条款上的 issue 没有
可对照的缺陷。因此 precision 是**以条款正确为条件的** —— 不是对排序的第二次评分。
recall 不设条件：它覆盖全部 gold 缺陷，包括那些落在 agent 只字未提的条款上的。

### 两种 null，因为工具本身必须被验证

一个对什么都说「aligned」的 LLM 判官会给出一个好看但毫无意义的数字。`--control` 把每条
issue 重新配对到不属于它的候选缺陷上：

- **`corpus`** —— 候选来自**不同案件**。当事人、标的、语汇全都不同。这能抓住那种只是
  认得出法律文体的判官。
- **`case`** —— 候选来自**同一案件的另一个条款**。当事人、文书、语汇都相同，只有缺陷
  不同，所以通过这一关意味着判官区分的是**缺陷**而不是**文档**。它的期望值**不是零**：
  法院把两个条款放在一起解释时，确实可能在两者上得到同一个缺陷 —— 所以它是一个噪声底，
  不是纯粹的 null。

两者都写到 `output/` 之外：

```bash
python src/experiments/issue_alignment_check.py --control corpus --out /tmp/ctl
python src/experiments/issue_alignment_check.py --control case   --out /tmp/ctl
```

### 控制组说明了什么

在所报告的这次运行上，`case` 控制是真实命中率必须对照的基准，而它并不是均匀分布的：

| | 主实验 | 控制（同案） | 比值 |
|---|---|---|---|
| 全部 issue | 33.0% | 14.2% | 2.3× |
| gold 1.1 — 词汇歧义 | 24.3% | 2.9% | **8.4×** |
| gold 2.2 — 整体一致性 | 35.2% | 26.4% | **1.3×** |

**这个工具在 1.1 上有效，在 2.2 上无效。** 关系型缺陷的描述形如「这一条要和那一条一起
读」，而在 `case` 控制里，假配对往往**就是**同一份文书里的另一条，两边的描述几乎可以
互换。要分开报告这两个数；单一的合并命中率会掩盖其中一半是无信息的。

结果见 [REPORT_ZH.md](REPORT_ZH.md)。
