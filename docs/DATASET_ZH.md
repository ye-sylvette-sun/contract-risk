# 数据集（中文）

一个**有风险 / 无风险合同条款**的标注数据集，来自联邦法院判决书和随案提交的合同。
每一条条款都是从扫描件中逐字切出的原文。

```
10,102 行  |  170 positive / 9,932 negative   (1.7% positive)
53 个案件  |  87 份合同
225 个 issue  |  法院实际解释过的缺陷，逐个列出
```

一个 positive 带一组 **issue** —— 法院在这个条款上解释过的每一个不同缺陷各占一条
—— 所以 170 个条款上共有 225 个缺陷：126 条各带一个，36 条两个，8 条三个及以上。
这组列表就是在 issue 层面给模型打分时的分母。

**这里的每一个 issue，都是一个手持合同的读者能够看到的。** step 3 会问「要看到这个
缺陷需要读到什么」，构建过程丢弃其中 45 个依赖语料并不持有的材料的 issue —— 一封
邮件、一段交易习惯、一份从未提交的附件。如果这样使得某个被解释的条款一个 issue 都
不剩，**整份合同**都会被移除：实验要求模型判断一份合同的各个条款，只判断其中一部分
是另一个任务。同一条规则也会移除持有两个逐字节相同条款、其中一个被解释的合同 ——
读者看到的文字无法把它们区分开。

170 个 positive 之间共挂了 225 个 risk type code —— 1.1 × 141、1.3 × 8、2.2 × 76 ——
因为其中 29 个带不止一个。当案件的 Westlaw key 只给出一个候选码时，标注为
`taxonomy_provenance = westlaw`（91 个条款），模型没有选择余地；当案件有多个候选码
时，由模型在**这些候选**中选择，provenance 记为 `model`（79 个条款）。

**risk type 是一个案件级的事实，被套用到每一个缺陷上。** 候选码来自案件立案时的
Westlaw key，而 62 个案件中有 41 个的 key 只覆盖两大类型中的一个，因此该案的每个
缺陷都取那个类型，无论判决书实际怎么说。step 2 会把法官自己与类型有关的原话记入
`type_evidence`，并在原话指向另一类型时置 `type_evidence_conflict`（332 个 issue 中
有 19 个）—— 让这种分歧在数据里可见，而不是藏在标签里。

---

## 1. 标签的含义

> **Positive** —— 判决书显示双方争过这个条款，且法院讨论了它，**无论法院最终怎么判**。

诉讼本身就是代价。一个必须在联邦法官面前争论过的条款，已经没有完成它的工作，即使
法官最终按起草者的本意解读它 —— 所以被法院**支持**、或被认定**清楚**的条款，和被
不利解释的条款同样算数。

> **Negative** —— 同一案件中提交的任何合同的任何其他条款。

未被诉讼的条款是**风险更低，而不是没有问题**：它可能起草良好，也可能带着无人有机会
去争的缺陷。针对这套标签算出的 precision 是一个下界。

risk *type* 来自案件立案时的 Westlaw Key Number，不来自模型的意见 —— 只有当案件立案
时挂了多个 key，才由模型说明争议落在**其中哪一个**上，并由 `taxonomy_provenance`
记录这件事。risky / not 这个二元标签从不依赖于此。

### 六个类型码

| code | risk type |
|---|---|
| 1.1 | 词汇歧义 —— 某个词或短语存在不止一种合理读法 |
| 1.2 | 机械错误 —— 书写、语法、拼写或标点上的错误 |
| 1.3 | 概括与列举 / 列表范围 —— 兜底表述与列举出的具体项相抵 |
| 2.1 | 条款冲突 —— 本条与另一条无法调和 |
| 2.2 | 整体一致性 —— 含义只有把合同作为整体阅读时才浮现 |
| 2.3 | 鉴于条款与正文 |

`1.x` 是条款自身文字的缺陷，`2.x` 是关系型缺陷。语料中实际出现的只有 1.1、1.3 和
2.2 三个码。

## 2. 核心原则：定位，而不是转写

模型从不书写条款正文。对每个条款，它返回一个行范围，外加两端各一个逐字锚点 ——
开头和结尾的各八个词，按扫描件所示原样抄录，包括 OCR 损坏。`lib.locate()` 把这些
锚点与合同文件比对，把边界吸附到锚点实际所在的位置，然后**从文件本身**切出文字。
锚点在声称的窗口附近匹配不到，说明模型指错了地方，该条款连同原因一起被拒绝。

`build_dataset.py` 随后按记录的字符偏移，从磁盘**重新切出每一行**并逐字节比对。
不一致就是构建失败，而不是一个警告。

## 3. 构建步骤

### Step 0 —— 建立语料（不用 LLM）

从 docket linking sheet 出发，逐级筛到可用的合同：

| | 协议数 | 案件数 |
|---|---|---|
| linking sheet 中 | 9,055 | 3,596 |
| 有 Bloomberg **Entry Document** 链接（其余只引用了无法下载的附件） | **1,374** | 732 |
| 已下载、OCR、切行（Contract-Risk 项目的样本，不是筛选条件） | **209** | 120 |
| 落在范围内的案件：立案于 12 个 key 之一，且判决书文本在磁盘上 | 143 | 81 |
| Contract-Risk 判定为 `usable` | 123 | 68 |
| 注册入库：0.90 shingle 包含度去重，长度达标 | **117** | 68 |
| 单栏排版：step 0b 拒绝 14 份双栏扫描件 | **103** | 62 |

这里每一道筛选都只关乎文档是否**可用**，没有一道关乎标签。Westlaw key 跨多个
taxonomy 码的案件会被保留：每个缺陷落在哪个码上逐 issue 记录，`taxonomy_provenance`
说明该案是否给模型留下了选择空间。

### Step 1 —— 切出一份合同的全部条款（`gpt-5.6-sol`，high effort，每份合同一次调用）

在**不看判决书**的情况下枚举一份合同的每一个条款，因此条款边界不可能依赖于法院说过
什么。这是 positive 和 negative 成为同一类对象的原因。

### Step 2 —— 哪些条款被争过、争的是什么（`gpt-5.6-sol`，high effort，每案一次调用）

给定判决书、该案的全部合同、以及 step 1 给出的条款清单，指出**清单中哪些条款**被
双方争过，以及法院在每个条款上解释了**哪几个不同的缺陷**。

每个 issue 携带：一句话说明缺陷、一个 risk type 码、以及判决书中相应段落的行范围。
**返回零个条款是合法答案**，当被争的协议从未提交时就会发生：62 个案件中有 7 个返回
零条款。法院解释过、但清单中没有任何条款包含的文字，进入 `unlocated` —— 记录这次
遗漏，而不是拿一个相近的条款顶替。这样的记录共 48 条，分布在 22 个案件中；§6 有
细分。

### Step 3 —— 每个 issue 要看到什么才看得出来（`gpt-5.6-sol`，high effort，每案一次调用）

| scope | | 数据集中 |
|---|---|---|
| `clause` | 仅凭引用的条款本身就能说明缺陷 | 97 |
| `contract` | 需要同一合同的其他条款 | 89 |
| `case` | 需要同案提交的另一份文书，记在 `scope_needs` | 39 |
| `external` | 语料并不持有的案件专属材料 | *丢弃* |

**通用知识不算 `external`** —— 法律、术语、常识都不算。只有本案专属的、语料之外的
材料才算。

### `build_dataset.py`（不用 LLM）

把每一行从磁盘重新切出并逐字节校验，拼装列，写出 `dataset.csv`。

## 4. 列

| 列 | |
|---|---|
| `citation`, `key` | 案件，及其立案所用的 Westlaw key |
| `taxonomy` | risk type 码，逗号分隔 —— 一个条款可以同时带 1.x 和 2.x |
| `taxonomy_provenance` | `westlaw`（该案只有一个码，没有模型参与）或 `model`（该案有多个码，由模型指出适用哪些） |
| `clause_id` | `c001…`，**在合同内**按文档顺序编号 —— 由 step 1 在任何标签存在之前指定 |
| `clause_name`, `label` | `POSITIVE` / `NEGATIVE` |
| `provenance` | 该行由哪一步产生 |
| `case_desc` | 一句话说明争议 |
| `contract_id`, `contract_file` | 从哪份文书切出 |
| `context_contract_ids` | 同案提交的其他合同，逗号分隔 —— step 2 看到的材料，也是读者要触及 `case` 级 issue 时需要挂载的东西。案件只有一份文书的 3,197 行为空 |
| `source_lines`, `source_span` | 锚点吸附到的行范围与字符偏移 |
| `clause_text` | 规范化后的抽取结果 —— **数据集正文** |
| `issues` | JSON 列表，每个记录的缺陷一条：`issue` 句子、`risk_type`、`type_evidence`、`type_evidence_conflict`、`scope`、判决书行范围与原文段落 |

## 5. 已知限度

- **条款长度可以区分两类，这是首要注意事项。** positive 的中位长度 619 字符，
  negative 是 343，仅凭长度排序的 ROC-AUC 就有 **0.691**。任何模型的 AUC 都必须
  对照这个基线来读 —— agent 实验在 risk type 1 上超过它，在 risk type 2 上与它
  完全持平。

  条款边界由 step 1 切出，而 step 1 从不看判决书，所以这个长度差是被诉讼语言本身的
  性质，不是切分方式造成的。
- **一个 positive 不等于一次独立争议，但它的 issue 是数得清的。** 225 个 issue 对应
  137 个不同的判决书段落：法院常在一段讨论里解释多个条款，所以一个段落可以服务多个
  条款。真正分开的是**缺陷** —— 每个 issue 各自命名一个。
- **332 个 issue 中有 45 个需要语料并不持有的材料**，它们连同因此再无可评分 positive
  的合同一起被丢弃。其中多数**不是缺失的文书**：它们依赖的是当事人做过什么的证据 ——
  邮件、交易习惯 —— 而不是某份文书。法院判定解释争议时依据的东西多于文书本身，一个
  由文书组成的语料永远无法容纳全部。
- **语料中每一份合同都是端到端可评分的。** 一个模型读得到、却无法被评分的条款会连带
  移除它所在的合同，所以没有任何条款清单是残缺的。
- **39 个存活的 issue 需要同案的另一份文书**，37 个 positive 依赖于此。
  `context_contract_ids` 指明需要挂载什么；只给模型一份合同的实验触及不到它们。
- **scope 标注是模型的判断**：重测一致率 90–93%，没有人工校验。
- **条款到段落的对应是模型的判断，不是已核实的事实。** 机械核实过的是：条款正文在
  提交的合同中逐字定位成功（`anchor_score` 均值 0.998，10,102 行中 9,958 行精确
  匹配），以及 taxonomy 是案件 Westlaw key 码的子集。**没有**核实的是：所附段落是否
  真的在讨论那个条款。对若干十条 positive 做人工抽查可以给出一个数字，这件事尚未做。
- **48 处法院解释过的内容不在数据集中**，记录在 `disputes.json` 的 `unlocated` 里，
  分布于 62 个案件中的 22 个。其中 32 处是语料不持有的文书 —— 从未提交的附件、不在
  附件中的保单 —— 另外 16 处是 step 1 未枚举到的文字。影响在 recall 上：它们是数据集
  缺少的行，不是判错的行。
- **两个正确锚点之间的过度捕获无法检测。** 一个从正确起点跨到正确终点、中间却多含了
  内容的范围，会通过全部校验。
