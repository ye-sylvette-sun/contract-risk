# 合同条款风险数据集 · 说明（中文）

```
10,358 行  |  179 positive / 10,179 negative  (1.7% positive)
57 个案件  |  89 份合同                        |  12.3 MB
242 个 issue |  法院实际解释过的缺陷，逐个列出
```

每个 positive 挂着一个 **issue 列表**——法院在这一条上解释过的每一个不同缺陷各
占一条——所以 179 个条款上一共有 242 个缺陷：125 条只有一个，48 条有两个，6 条
三个以上。这个列表就是 issue 级评分的分母，上一版数据集给不出来。

**这里的每一个 issue，都是一个拿着合同的读者够得着的。** Step 3 逐条问"要看出这
个缺陷必须能读到什么"，然后丢掉那 43 个依赖语料没有的材料的 issue（一封邮件、一段
交易惯例、一份从未归档的附件）。如果这让某个被法院解释过的条款一条 issue 都不剩，
**整份合同**一起丢弃——实验是让模型判一份合同的全部条款，只判其中一部分是另一回事。

179 个 positive 之间一共挂了 242 个 risk type code（1.1 × 170、1.3 × 7、
2.2 × 65），因为其中 24 个同时挂了不止一个。案件的 Westlaw key 只对应一个候选
code 时，标签是纯 Westlaw 事实（`taxonomy_provenance = westlaw`，103 条）；案件
有多个候选时由模型在其中选择（`model`，76 条）。

## 1. 数据是怎么串联在一起的

我们最终要的是一张表，每一行是**一个合同条款**，外加一个标签：这个条款有没有被法院拿去解释过。

难点在于"条款"和"风险"不在同一个地方——条款在合同里，而"这个条款出过问题"只记录在判决书和 Westlaw 的分类体系里。所以整件事本质上是把几份互不相干的材料对齐，让它们顺着一条链走通：

```
Westlaw 分类号 (key)
      │   每个分类号下面挂着一批案件，各配一段判例摘要
      ▼
判例摘要 (headnote)  ──── 它属于哪个案件，写在摘要旁边
      │
      ▼
具体案件 (court case)  ──┬── 判决书全文（法院说了什么）
      │                  └── 卷宗归档文件（当事人交上去的东西）
      ▼
该案归档的合同 (contract)
      │
      ▼
合同里的每一个条款 (clause)  ←── 数据集的一行
```

**Westlaw 分类号**是法律实务用的主题分类。我们只关心其中 12 个，它们讲的都是"合同条款该怎么解释"这一类问题。

**判例摘要**是 Westlaw 为每个案件写的一句话要点，挂在分类号底下，旁边写着它属于哪个案件。顺着它就能从"分类号"走到"具体案件"。

**案件**同时连着两样东西：判决书全文（法院说了什么）和卷宗归档文件（当事人交上去的东西，合同就在里面）。

**合同**再拆成一个个**条款**，就是数据集的clause。

### 我们自己定义的 risk type

12 个 Westlaw 分类号粒度不齐、名字也是行话，我们把它们归并成 **6 种 risk type**，分两个大类：

**第 1 类 —— 缺陷在条款自己的文字里**，只读这一条就能看出来：

| 编号 | risk type | 对应分类号 |
|---|---|---|
| 1.1 | **词句歧义**：某个词或短语确实有一个以上的合理解读 | 143(2)、152、159 |
| 1.2 | **机械错误**：笔误、语法、拼写、标点上的错误影响了意思 | 157、158 |
| 1.3 | **概括词与列举项**：兜底表述挨着一串具体列举，范围说不清；或条款过于一边倒，有歧义时会被作不利于起草方的解释 | 156、155 |

**第 2 类 —— 缺陷在这一条与合同其余部分的关系里**，必须读整份合同：

| 编号 | risk type | 对应分类号 |
|---|---|---|
| 2.1 | **条款冲突**：与同一合同的另一条直接矛盾 | 162 |
| 2.2 | **全文一致性**：意思只有通读整份合同才成立（或才崩掉） | 143.5、147(3)、161 |
| 2.3 | **鉴于条款 vs 正文**：前言陈述和正式条款指向不同方向 | 160 |

## 2. Step 0：从外部数据到 103 份合同

### 2.1 taxonomy 先圈定案件范围

那 12 个分类号（即上面的 risk type 1.x 和 risk type 2.x）决定了哪些案件在范围内。一个案件被留下的条件有三个：

1. 出现在这 12 个分类号之下；
2. 判决书全文拿得到；
3. 卷宗对照表显示该案至少有一份可下载的归档文件——能拿到合同全文。

三个条件同时满足的有 **475 个案件**。注意 taxonomy 是在**案件层面**起筛选作用的：它决定哪些案件值得去取合同，之后的筛选就都是合同层面的可用性问题了。

### 2.2 教授的GitHub仓库（Contract-Risk）提供了什么

合同文本不是我们自己处理的。Contract-Risk 项目针对上面这批案件，已经完成了四件事：

1. **下载**该案卷宗里的归档文件；
2. **OCR**，把扫描件转成文字；
3. **定位**：让模型判断哪个文件里装的是哪份具名协议，然后按行号把该协议自己的部分切出来——**这是一次逐行原样切割，模型只给行号，文字一个字没改**；
4. **核验**：把切出来的东西对着判决书检查两件事——这是不是法院当时在解释的那份合同？读得了吗？结论记为一个 verdict。

不过教授的数据覆盖的案件远不止我们需要的——其中大部分属于别的 Westlaw 分类号。与 risk type 1、risk type 2 那 12 个分类号对得上的一共 **81 个案件**，我们目前只用这 81 个。

这 81 个案件交付了 143 份切好的合同，之后还要再筛几道，详见下表。

### 2.3 从 1,374 份可下载协议到 103 份合同

每一级筛选和它留下的数量。这些数字都可以从 `data/`、`contract_risk/generated/`
和 `output/{cases,contracts,layout}.json` 重新算出来。

| | 协议 | 案件 |
|---|---:|---:|
| 卷宗对照表里的全部 | 9,055 | 3,596 |
| 带 Bloomberg **Entry Document** 链接的——其余的只写了附件编号，文件下载不到 | **1,374** | 732 |
| Contract-Risk 已下载、OCR、按行切好的——*这是抽样，不是筛选* | **209** | 120 |
| 落在范围内的案件里：12 个 key 之一，且判决书正文在磁盘上 | 143 | 81 |
| Contract-Risk 自己的 verdict 为 `usable` | 123 | 68 |
| 注册进 registry——8 词 shingle 包含度 0.90 去重、过字数下限 | **117** | 68 |
| 单栏——step 0b 剔除 14 份双栏扫描件 | **103** | 62 |

这是**语料**。`build_dataset.py` 之后还会再丢掉 14 份——它们被法院解释过的条款，没
有一个是合同读者够得着的——最终数据集是 **89 份**。

现在每一条筛选都只关于"文件能不能用"，**没有关于标签的筛选了**。

上一版曾多加一条：案件的全部 Westlaw key 必须映射到同一个 taxonomy code 才保留，
代价是 42 份合同。现在这条性质**逐行**去买，用 `taxonomy_provenance` 这一列，不用
再丢数据：

- **案件只有一个 code** —— 没得选，code 就是 Westlaw 事实，`taxonomy_provenance
  = westlaw`。
- **案件有多个 code** —— 我们把完整的六类 taxonomy 作为背景、把该案件自己的
  code 作为**候选**一起给模型，让它说这一条条款的争议落在候选中的哪个（可以多
  选：法院完全可能既认为某个词本身有歧义、又要靠通读全文才能定），
  `taxonomy_provenance = model`。候选之外的一律拒收。

注意**二元标签（risky / not risky）从头到尾不受影响**——positive 之所以是
positive，是因为判决书显示法院解释过它，与 key 挂几个 code 无关。受影响的只有
risk *type* 这一列。想要更严格数据集的人，按 `taxonomy_provenance == "westlaw"`
过滤即可（179 个 positive 中的 103 个）。

## 3. Step 1：把每一份合同的全部条款切出来

**条款的边界只在这一步决定**，正例负例都一样。

这一步是故意排在最前面、也是故意"什么都不知道"的：它只看到一份合同，看不到判决
书、看不到 Westlaw 分类号、也不知道这份文件是否上过法庭。条款边界是**起草本身的
事实**，不能因为法院碰巧解释了哪一条而移动。

每个条款拿到一个编号——按文档顺序的 `c001`、`c002`……——step 2 只能用这些编号作答。

**为什么要改成这个顺序。**原来是争议那一步在前，它自己切 span，边界会跟着法院说了
什么漂移——把一个条款拆成三段好让每段各挂一个缺陷，或反过来撑大好装下两个。这种漂
移是正例和负例之间一个**与起草风险无关**的系统性差别，而分类器学得会。

模型只给"位置"：第几行到第几行，外加**开头 8 个词**和**结尾 8 个词**——照扫描件
原样抄，OCR 错字也一起抄。程序拿这首尾两串词回到文件里比对、对齐，然后**从文件本
身把这段文字切出来**。对不上就作废。

条款按 span 排序后写出，所以产物不依赖模型报告的顺序。两个过度捕获检测器随后以
**flag** 形式运行（span 重叠、长度超过该合同中位数 10 倍），只记录不拒收，103 份
合同里有 35 份带 flag。

## 4. Step 2：哪些条款被争过，争的是什么

这一次把**判决书、该案全部合同、以及 step 1 给每份合同的条款清单**一起交给模型
（`gpt-5.6-sol`，一个案件一次）。模型回答哪些条款被争过——**用编号**——以及每一条
上有哪些 issue。

一个 issue 就是法院解释过的一个不同缺陷，各自带着自己的 risk type 和自己的那段判
词。两条 entry 意味着两个不同的问题；法院在判决书后面又回头说了一遍同一个缺陷，
仍然算一个 issue。一个条款既被argue措辞有歧义、又被argue与另一节冲突，那是**两个
issue**，而不是一个条款挂两个 code。

**它没有能力报告 span。** schema 里根本没有行号和 anchor 字段，不在清单里的编号
直接被拒收。所以逐字保证不变——`build_dataset.py` 仍然从文件重切每一行——但边界属
于那个没看过判决书的步骤。

为什么"被讨论过"就算 high risk：我们的目标是避免自己写的条款将来被对方抓住去
attack。一个条款只要被拿到法官面前争过，它就已经失败了——**法院最后判谁赢并不重
要**。哪怕法官认定这一条"清晰、无歧义"，它照样算 positive。

**返回"一条都没有"是合法答案**，62 个案件里有 6 个如此，通常是因为被争的那份协议
根本没有归档。如果法院解释的语言不在任何清单条款里，它进 `unlocated`——记录这次漏
检，而不是随便报一个最接近的条款。这样的有 43 条，分布在 21 个案件里。

## 4.5 Step 3：每个 issue 要看到什么才看得出来

Step 2 是**拿着该案全部合同**做标注的，而实验只给模型一份。所以数据里可能存在一
些"读目标合同的人永远找不到"的 issue，而且从数据本身看不出是哪些。这一步就是把
它们标出来。

它带上**带行号的完整判决书**、该案全部合同、以及 step 2 记录的每一个 issue，逐条
回答**读者必须握有什么**：

| scope | | 数据集中 |
|---|---|---|
| `clause` | 光看引用的这一条就能说出缺陷 | 119 |
| `contract` | 需要同一份合同的其他条款 | 84 |
| `case` | 需要同案件的另一份文书，在 `scope_needs` 里点名 | 39 |
| `external` | 语料没有的、本案特有的材料 | *丢弃* |

**世界知识不算 `external`** —— 法律、术语的行业含义、日常语义都算在读者这一侧。判
定标准是：缺的那样东西是不是**本案特有**、且不在已归档的文书里。

**它不改动任何标签。** `disputes.json` 只读不写；这一步只做标注，由
`build_dataset.py` 执行。

三次运行的重测一致率是四档 scope 上 90–93%、可达性判断上 97%。和"判词与条款的对
应关系"（第 5 节）一样，它是模型判断，没有程序性验证。

## 5. 两步之外：negative 从哪来

negative 就是 step 1 枚举出来、而 step 2 没有点名的那些条款——**一个编号的集合归属
判断**，没有别的。以前两步各切各的 span，还要用行号相交去算重叠；现在两类来自同一
次、不知道标签的枚举。

要注意 low risk 的准确含义是"**没人去争过**"，而不是"写得没问题"：它可能确实写得
好，也可能藏着毛病，只是没人有机会、或者不值得为它打一场官司。

再经 step 3 过滤掉够不着的那些，最后是：**179 个 positive + 10,179 个 negative =
10,358 个条款**，这就是数据集。

被 step 3 判为 `external` 的 issue 一律丢弃：任何 harness 都没法把它送到合同读者眼
前，拿它评分量的是卷宗而不是读者。如果这让某个 positive 一条 issue 都不剩，**整份
合同**一起丢弃——不是只丢那个条款，更不会改标成 NEGATIVE（那等于断言与法院相反的事
实）。只丢条款的话，实验交给模型的待判清单上会留一个洞，而且洞正好在法院发现缺陷
的地方；判一份合同的一部分不是这个任务。代价是 14 份合同、1,678 行、23 个
positive。存活行的 `opinion_comment` 按剩下的 issue 重建。

### 关于 positive 的几点限度

**长度是一条真实的捷径，这是最需要先知道的一条。** positive 中位数 588 字符，
negative 330，单靠长度排序的合同内 ROC-AUC 就有 **0.712**。任何模型的 AUC 都要拿
它当基线读。上一版这个数是 0.523，但那才是假象：当时的 positive 由**读过判决书**
的模型来切，边界贴着争议那段话而不是完整条款——那是一个**依赖标签的边界**，比它掩
盖的混淆更严重。过度捕获也解释不了现在这个数：step 1 没打 flag 的合同里 AUC 反而
更高（0.749 对 0.665）。

**一个 positive 不等于一次独立的争议，但缺陷现在数得清了。** 242 个 issue 对应
**139 段不同的判词**——法院常在一段论述里同时解释好几个条款，所以一段判词可以服务
多个条款。变了的是**缺陷**本身：每个 issue 各自命名一个，所以"法院在这一条上找到
了几个问题"现在有答案了。

**43 处法院解释过的语言不在数据集里**，记录在 `disputes.json` 的 `unlocated` 里：
39 处是语料根本没有的文件，4 处是 step 1 没枚举到的文本。**没有一处变成错标的
negative**——这 4 处都落在所有已枚举 span 之外，是"缺行"而不是"标错行"。影响的是召
回，不是标签的可靠性。注意这和下一条里 step 3 的 43 个 `external` **是两回事**，数
字相同纯属巧合：`unlocated` 是 step 2 没能挂到任何条款上的，`external` 是挂上了、
但 step 3 判定够不着的。

**310 个 issue 里有 43 个依赖语料没有的材料，连同因此没有可计分 positive 的 14 份
合同一起丢弃。** 其中多数**不是缺文件**：
26 个依赖当事人做过什么的证据（伪造的邮件、一段交易惯例），17 个依赖卷宗里没有的
文书。法院判构解争议靠的从来不止合同本身，而一个合同语料永远装不下其余部分。留下
的 39 个 `case` issue（涉及 36 个 positive）需要挂上同案件的姊妹文书才够得着，
`context_contract_ids` 写明了要挂哪些。这份 scope 标注和下面那条一样是模型判断，
重测一致率 90–93%，没有人工核验。

**还有 4 份合同的待判清单上留着洞。** 上面"逐字重复 positive 就丢弃"那条规则丢掉了
16 个条款却没有丢掉它们所属的合同，所以模型判这 4 份时，并没有被问到它读得到的每一
个条款。这些条款是批单之间重复的样板文字，不是被争议过的语言。

**"这段判词讲的就是这一条"是模型的判断，不是被验证的事实。** 程序硬验证的是两
件事：条款正文逐字定位到了合同原件（`anchor_score` 均值 0.997，10,358 行里
10,095 行精确命中），以及 taxonomy
是该案 Westlaw key 码的子集。没有验证的是判词与条款的对应关系——这个链接由提取模
型建立，曾经用来复核它的启发式规则因为过于 ad hoc 已被移除。人工抽查几十条能给出
一个数字，这件事还没做。

## 6. 哪些环节是 LLM 做的

| 环节 | 谁在做 |
|---|---|
| 串联案件、注册合同 | 程序，不用模型 |
| 剔除双栏扫描件 | 一个便宜的模型（`gpt-5.6-terra`）读跨全文抽样的若干窗口，并**逐字引回交错的行和行号**，让每次剔除都可以回原文复核 |
| **Step 1** 列出每份合同的全部条款、定边界 | 模型（`gpt-5.6-sol`），一份合同一次调用 |
| **Step 2** 说哪些编号被争过、争的是什么 | 模型（`gpt-5.6-sol`），一个案件一次调用 |
| **Step 3** 说每个 issue 要读到什么才看得出来 | 模型（`gpt-5.6-sol`），一个案件一次调用 |
| 组装、校验、导出数据集 | 程序，不用模型 |

有两件事**模型自始至终没有参与**：

- **条款的正文**。模型只给位置，文字一律由程序从合同文件里切，切完只做三件事——去掉页码和法院盖的戳、把断行处被拆开的词接回去、压掉多余空格。错字、漏字、标点一律原样保留。
- **风险类别（1.1 / 2.2 之类）**。它来自这个案件被 Westlaw 归在哪个分类号下，是既定事实。模型只能在这个案件已有的编号里挑一个，挑到别的一律作废。

最后，程序会把每一行都**按记录的位置回到原文件重切一遍**，必须逐字一致才允许写出数据集——所以哪怕模型在中间环节出过错，也不可能有一行"文件里根本没有的文字"混进来。
