# 合同条款风险数据集 · 说明（中文）

---

## 1. 数据是怎么串联在一起的

我们最终要的是一张表，每一行是**一个合同条款**，外加一个标签：这个条款有没有被法院拿去解释过。

难点在于"条款"和"风险"不在同一个地方——条款在合同里，而"这个条款出过问题"只记录在判决书和 Westlaw 的分类体系里。所以整件事本质上是把几份互不相干的材料对齐，让它们顺着一条链走通：

```
Westlaw 分类号 (key)
      │   每个分类号下面挂着一批案件，各配一段判例摘要
      ▼
判例摘要 (headnote)  ──── 它属于哪个案件，写在摘要旁边
      │
      ▼
具体案件 (court case)  ──┬── 判决书全文（法院说了什么）
      │                  └── 卷宗归档文件（当事人交上去的东西）
      ▼
该案归档的合同 (contract)
      │
      ▼
合同里的每一个条款 (clause)  ←── 数据集的一行
```

**Westlaw 分类号**是法律实务用的主题分类。我们只关心其中 12 个，它们讲的都是"合同条款该怎么解释"这一类问题。

**判例摘要**是 Westlaw 为每个案件写的一句话要点，挂在分类号底下，旁边写着它属于哪个案件。顺着它就能从"分类号"走到"具体案件"。

**案件**同时连着两样东西：判决书全文（法院说了什么）和卷宗归档文件（当事人交上去的东西，合同就在里面）。

**合同**再拆成一个个**条款**，就是数据集的clause。

### 我们自己定义的 risk category

12 个 Westlaw 分类号粒度不齐、名字也是行话，我们把它们归并成 **6 种 risk category**，分两个大类：

**第 1 类 —— 缺陷在条款自己的文字里**，只读这一条就能看出来：

| 编号 | risk category | 对应分类号 |
|---|---|---|
| 1.1 | **词句歧义**：某个词或短语确实有一个以上的合理解读 | 143(2)、152、159 |
| 1.2 | **机械错误**：笔误、语法、拼写、标点上的错误影响了意思 | 157、158 |
| 1.3 | **概括词与列举项**：兜底表述挨着一串具体列举，范围说不清；或条款过于一边倒，有歧义时会被作不利于起草方的解释 | 156、155 |

**第 2 类 —— 缺陷在这一条与合同其余部分的关系里**，必须读整份合同：

| 编号 | risk category | 对应分类号 |
|---|---|---|
| 2.1 | **条款冲突**：与同一合同的另一条直接矛盾 | 162 |
| 2.2 | **全文一致性**：意思只有通读整份合同才成立（或才崩掉） | 143.5、147(3)、161 |
| 2.3 | **鉴于条款 vs 正文**：前言陈述和正式条款指向不同方向 | 160 |

## 2. Step 0：从外部数据到 67 份合同

### 2.1 taxonomy 先圈定案件范围

那 12 个分类号（即上面的 category 1.x 和 category 2.x）决定了哪些案件在范围内。一个案件被留下的条件有三个：

1. 出现在这 12 个分类号之下；
2. 判决书全文拿得到；
3. 卷宗对照表显示该案至少有一份可下载的归档文件——能拿到合同全文。

三个条件同时满足的有 **475 个案件**。注意 taxonomy 是在**案件层面**起筛选作用的：它决定哪些案件值得去取合同，之后的筛选就都是合同层面的可用性问题了。

### 2.2 教授的GitHub仓库（Contract-Risk）提供了什么

合同文本不是我们自己处理的。Contract-Risk 项目针对上面这批案件，已经完成了四件事：

1. **下载**该案卷宗里的归档文件；
2. **OCR**，把扫描件转成文字；
3. **定位**：让模型判断哪个文件里装的是哪份具名协议，然后按行号把该协议自己的部分切出来——**这是一次逐行原样切割，模型只给行号，文字一个字没改**；
4. **核验**：把切出来的东西对着判决书检查两件事——这是不是法院当时在解释的那份合同？读得了吗？结论记为一个 verdict。

不过教授的数据覆盖的案件远不止我们需要的——其中大部分属于别的 Westlaw 分类号。与 category 1、category 2 那 12 个分类号对得上的一共 **81 个案件**，我们目前只用这 81 个。

这 81 个案件交付了 143 份切好的合同，之后还要再筛几道，详见下表。

### 2.3 从 1,374 份可下载协议到 67 份合同

每一级筛选和它留下的数量。这些数字都可以从 `data/`、`contract_risk/generated/`
和 `output/{cases,contracts,layout}.json` 重新算出来。

| | 协议 | 案件 |
|---|---:|---:|
| 卷宗对照表里的全部 | 9,055 | 3,596 |
| 带 Bloomberg **Entry Document** 链接的——其余的只写了附件编号，文件下载不到 | **1,374** | 732 |
| Contract-Risk 已下载、OCR、按行切好的——*这是抽样，不是筛选* | **209** | 120 |
| 落在范围内的案件里：12 个 key 之一，且判决书正文在磁盘上 | 143 | 81 |
| Contract-Risk 自己的 verdict 为 `usable` | 123 | 68 |
| 注册进 registry——8 词 shingle 包含度 0.90 去重、过字数下限 | **117** | 68 |
| 单栏——step 0b 剔除 8 份双栏扫描件 | **109** | 68 |
| 案件只挂**一个 risk category** | **67** | **39** |

最后一行是唯一一条关于**标签**而非"文件能不能用"的筛选，代价也最大。

**规则本身。** 一个案件的全部 Westlaw key 必须映射到同一个 taxonomy code 才保留。
key 有多个没关系——保留的 44 个案件里有 7 个带两个 key，但指的是同一种风险
（`k143.5` 与 `k147(3)` 都映射到 2.2）。被排除的是 key 跨了两个 code 的案件。

## 3. Step 1：被法院讨论过的条款 = high risk

一个案件跑一次，把判决书和该案的合同一起交给模型，让它找出**判决书里被讨论过的条款**：双方各执一词、法官也确实展开讨论了的那些。这些条款就是 positive（high risk）。

为什么"被讨论过"就算 high risk：我们的目标是避免自己写的条款将来被对方抓住去 attack。一个条款只要被拿到法官面前争过，它就已经失败了——**法院最后判谁赢并不重要**。哪怕法官认定这一条"清晰、无歧义"，它照样算 positive，因为对方能拿它做文章这件事本身已经发生了。

**模型在这里具体做什么。**我们把整篇判决书和该案的全部合同一起交给模型（Claude Opus 5），问它哪些条款被讨论了、在哪里。但**模型不负责抄条款正文**，它只回一个"位置"：条款在第几行到第几行，外加**开头 8 个词**和**结尾 8 个词**——照扫描件原样抄，OCR 错字也一起抄。程序再拿这首尾两串词回到合同文件里比对、对齐，然后**从文件本身把这段文字切出来**。对不上，就说明模型指错了地方，这一条直接作废。

这样数据集里的每一个字都来自合同原件，模型没有机会"顺手改通顺"。此外每报一个条款，模型还必须指出判决书里讨论它的是哪一段，这段话会一并存下来当证据。

## 4. Step 2：合同里剩下的条款 = low risk

再对每一份合同跑一次，这次不给判决书，让模型把这份合同的**全部条款**从头到尾逐条列出来。定位方式和 step 1 完全一样——模型只给行号和首尾各 8 个词，正文由程序从文件里切。

这里要说清楚一点：**模型并不知道 step 1 找出的是哪一条**。step 2 的输入只有合同全文，判决书和 step 1 的结果都没有传进去，所以它列出来的清单里通常也包含那条 positive。重合的部分是事后由 `build_dataset.py` 按**行号区间相交**剔除掉的，剩下的才是 negative（low risk）。

之所以不把 step 1 的答案告诉模型：一旦它知道哪条被争过，它列其余条款时的行为就可能被这个信息带偏——比如避开语义相近的条款，或者反过来专挑能与之对照的条款。那样两类之间的差别就不止"有没有被争过"这一项了。现在 negative 和 positive 来自同一批合同、同一次抽取、同一套定位方式，唯一的系统性差别就是"有没有被争过"。

要注意 low risk 的准确含义是"**没人去争过**"，而不是"写得没问题"：它可能确实写得好，也可能藏着毛病，只是没人有机会、或者不值得为它打一场官司。

两步加起来：**144 个 positive + 6,691 个 negative = 6,835 个条款**，这就是数据集。

## 5. 哪些环节是 LLM 做的

| 环节 | 谁在做 |
|---|---|
| 串联案件、注册合同 | 程序，不用模型 |
| 剔除双栏扫描件 | 一个便宜的模型（Sonnet 5）看几段文字判断，外加一条免费的排版规则，两者任一说是就剔除 |
| **Step 1** 找出被讨论过的条款 | 模型（Opus 5），一个案件一次调用 |
| **Step 2** 列出其余条款 | 模型（Opus 5），一份合同一次调用 |
| 组装、校验、导出数据集 | 程序，不用模型 |

有两件事**模型自始至终没有参与**：

- **条款的正文**。模型只给位置，文字一律由程序从合同文件里切，切完只做三件事——去掉页码和法院盖的戳、把断行处被拆开的词接回去、压掉多余空格。错字、漏字、标点一律原样保留。
- **风险类别（1.1 / 2.2 之类）**。它来自这个案件被 Westlaw 归在哪个分类号下，是既定事实。模型只能在这个案件已有的编号里挑一个，挑到别的一律作废。

最后，程序会把每一行都**按记录的位置回到原文件重切一遍**，必须逐字一致才允许写出数据集——所以哪怕模型在中间环节出过错，也不可能有一行"文件里根本没有的文字"混进来。
